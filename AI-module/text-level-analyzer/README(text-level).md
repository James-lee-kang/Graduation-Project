# text-level-analyzer

공공 웹사이트 접근성 자동 평가 플랫폼 **UniAccess**의 텍스트 난이도 분석 모듈.  
rule-based-analyzer가 저장한 렌더링 HTML에서 텍스트를 추출하고, 한국어 인지 난이도를 자체 설계 공식으로 측정한 뒤, 위반 항목에 대해 수정 제안을 자동 생성한다.

---

## 파일 구성

```
text-level-analyzer/
├── text_extractor.py        HTML → 텍스트 추출 + 종류별 분류
├── difficulty_engine.py     텍스트 → 한국어 인지 난이도 점수 산출
├── suggestion_generator.py  난이도 위반 항목 → 수정 제안 생성 (규칙 기반 + LLM)
├── text_standard_mapper.py  난이도 플래그 → WCAG 2.2 / KWCAG 항목
├── compute_pair_difficulty.py  설문 원문·수정문 쌍에 같은 공식을 사후 적용
├── export_study_pairs.py    설문용 원문·수정문 블라인드 쌍 추출
├── test_*.py                단위 테스트 5개 파일, 95개 (test_difficulty_engine.py 70개, 2026-10-13 기준)
├── korean_vocab_grades.json 국립국어원 학습용 어휘 등급 사전 (A/B/C 등급, 5543개)
├── web_common_words.json    웹 인터페이스 어휘 55개 (로그인·검색·게시판 등, 쉬운 단어 W로 취급, 2026-10-04)
└── .env                     OpenAI API 키 (git 제외, 직접 만듦)
```

---

## 파이프라인 내 위치

```
[rule-based-analyzer]
  run.js → result.html (렌더링된 DOM 저장)
                ↓
[text-level-analyzer]
  text_extractor.py       → output/result_text.json
  difficulty_engine.py    → output/result_text_difficulty.json
  mapping.js(KWCAG 2.2) → text_standard_mapper.py
  suggestion_generator.py → output/result_text_suggestions.json
                ↓
[run_all.py]
  세 모듈 결과 통합 → result_final.json → 백엔드 전송
```

run_all.py가 세 단계를 순서대로 자동 실행하므로, 개별 실행은 개발·디버깅 목적으로만 사용한다.
레이어 팝업이 있으면 run_all.py가 `result_popup.html`도 같은 세 단계로 분석해 결과 블록 뒤에 `exclusion_reason: "POPUP"`으로 붙인다(점수에는 넣지 않음).
`text_standard_mapper.py`는 루트의 `standard_mapping.py`를 거쳐 `node rule-based-analyzer/mapping.js`를 실행하므로 이 모듈을 돌리는 PC에도 Node가 있어야 한다.

## 실행 방법

### 전체 파이프라인 (권장)

run_all.py가 있는 폴더(개인 저장소는 `graduation_project/`, 팀 저장소는 `Graduation-Project/AI-module/`)에서 실행하면 이 모듈의 세 단계가 자동으로 순서대로 실행된다.

```bash
cd graduation_project            # 팀 저장소라면 cd Graduation-Project/AI-module
python run_all.py https://example.go.kr
```

### 단계별 개별 실행 (디버깅용)

`text-level-analyzer/` 폴더 안에서 실행한다(파일 경로는 그 폴더 기준).

```bash
cd text-level-analyzer

# Step 1 — 텍스트 추출
python text_extractor.py ../output/result.html ../output/result_text.json
# 두 번째 인자를 빼면 입력과 같은 폴더의 result_text.json

# Step 2 — 난이도 분석
python difficulty_engine.py ../output/result_text.json
# → ../output/result_text_difficulty.json (입력 이름 + _difficulty)

# Step 3 — 수정 제안 생성
python suggestion_generator.py ../output/result_text_difficulty.json
# → ../output/result_text_suggestions.json

# 레이어 팝업 문서는 팝업 모드로 추출 (모달·팝업 제거 규칙을 끔)
python text_extractor.py ../output/result_popup.html ../output/popup_text.json --popup-layer
```

세 스크립트 모두 두 번째 인자로 출력 경로를 직접 지정할 수 있다.

### 테스트

```bash
python -m unittest discover -s text-level-analyzer -p "test_*.py"   # run_all.py가 있는 폴더에서, 95개 (2026-10-13)
```

`test_difficulty_engine.py`는 MeCab과 한국어 사전이 있어야 돌아간다. LLM 테스트는 실제 API를 부르지 않는다. `FrozenFormulaTest`는 대표 글 5개의 블록 점수(`difficulty_score`, `difficulty_score_v2`, 평균 문장 길이, 쉬운 단어 비율, GL)와 기준값을 숫자로 고정한다. 2차 설문의 검증 대상이 실수로 바뀌면 바로 실패한다. 2026-10-14 확인: 이 PC 사전(`C:/mecab`)은 문장 안의 "누리집"을 `누리`+`집`으로 쪼개고 클라우드 사전은 한 단어로 본다. 공식은 같고 단어 수만 하나 달라 블록 점수가 60.4 → 61.6이 되므로, 쪼개는 사전에서는 그 값을 기대한다. 텍스트 점수는 사전 버전에 따라 조금 달라질 수 있으니 측정은 한 PC에서 하고 사전을 밝힌다.

run_all.py가 있는 폴더의 `requirements.txt`에 세 모듈의 Python 패키지가 버전 고정으로 들어 있다. 이 모듈이 쓰는 것은 `beautifulsoup4`, `mecab-python3`, `python-dotenv`, `requests`다.

```bash
pip install -r requirements.txt
```

### MeCab 한국어 형태소 분석기 (Windows)

difficulty_engine.py는 MeCab을 사용하여 형태소 분석을 수행한다.  
Windows에서는 pip 설치만으로 동작하지 않으며, 아래 순서로 수동 설치가 필요하다.

1. [mecab-ko-msvc Releases](https://github.com/Pusnow/mecab-ko-msvc/releases)에서 다음 두 파일을 다운로드한다.
   - `mecab-ko-windows-x64.zip` — MeCab 바이너리
   - `mecab-ko-dic.zip` — 한국어 사전
2. 바이너리를 `C:\mecab\`에 압축 해제한다.
3. 사전을 `C:\mecab\share\mecab-ko-dic\`에 압축 해제한다.
4. `C:\mecab\etc\mecabrc` 파일을 생성하고 아래 한 줄을 작성한다.
   ```
   dicdir = C:\mecab\share\mecab-ko-dic
   ```
5. 설치 확인:
   ```bash
   python -c "import MeCab; t=MeCab.Tagger('-r C:/mecab/etc/mecabrc -d C:/mecab/share/mecab-ko-dic'); print(t.parse('접근성을 개선한다'))"
   ```

## 파일별 역할 설명

### text_extractor.py — 텍스트 추출 전처리

**입력:** `result.html` (rule-based-analyzer의 run.js가 저장한 렌더링된 DOM)  
**출력:** `result_text.json`

rule-based-analyzer가 저장한 렌더링 HTML에서 AI 분석 대상 텍스트를 깨끗하게 추출하고, 아래 10개 카테고리로 분류한다.

ARIA role을 먼저 보고, 없으면 태그 이름으로 분류한다. 기준값의 근거와 실제 검사 내용은 아래 difficulty_engine.py 절에 있다.

| 카테고리 | 대상 | 난이도 분석 기준 |
|---|---|---|
| `paragraph` | p, 그리고 article, section, main, div, span, blockquote | Jo(2016) 이독성 공식 전체 적용 (핵심 대상) |
| `heading` | h1~h6, role="heading" | 60자 초과 시 플래그 |
| `button` | button, input(submit, button, reset), role="button" | 20자 초과 시 플래그 |
| `link` | a | 30자 초과 시 플래그 |
| `label` | label, legend | 40자 초과 시 플래그 |
| `form_guide` | placeholder, aria-label, title 속성값 | 50자 초과 시 플래그 (보이는 글을 그대로 담은 title·aria-label은 제외) |
| `table` | th, td, caption | 평균 문장 길이 25어절 이상 (문장 끝 부호가 있는 글만) |
| `list` | li, dt, dd | 평균 문장 길이 25어절 이상 (문장 끝 부호가 있는 글만) |
| `alert` | role이 alert, status, log, marquee, timer | 평균 문장 길이 25어절 이상 (문장 끝 부호가 있는 글만) |
| `other` | em, strong, b, i, small, time, figcaption, summary, details, address 같은 인라인·보조 태그 | 평균 문장 길이 25어절 이상 (문장 끝 부호가 있는 글만) |

모든 카테고리에 감각 의존 지시·모호한 참조 탐지(2026-10-13에 위치 의존 표현 탐지를 좁혀 바꿈)와 명사 나열 검사가 공통으로 붙는다(2026-10-02).

처리 과정은 5단계로 구성된다.

1. 불필요한 태그 제거: `script`, `style`, `noscript`, `iframe`, `svg`, `math`, `template`, `code`, `pre`를 DOM에서 완전히 삭제한다. (그 전에 원래 형제 순서를 기록해, 요소를 지워도 `selector`의 `:nth-of-type(N)`이 실제 화면과 맞게 한다.)
2. HTML 주석 제거: `<!-- -->` 형태의 개발자 메모를 제거한다.
3. 숨겨진·제외된 요소 제거: rule-based-analyzer가 표시한 광고·동적 영역(`data-ua-excluded-region`)과 이 화면 폭에서 안 그려지는 요소(`data-ua-hidden`), 인라인 `display:none`, `aria-hidden="true"`, `role="dialog"`, class가 `modal`·`popup`·`loading`·`layer-loading`인 요소, id에 `modal`·`popup`·`tracer`·`loading`·`wait`가 들어간 요소를 제거한다. 정부24 실제 테스트 중 대기열 페이지(TRACER)·모달이 분석 대상으로 잡히는 문제가 발견되어 추가된 단계다. 스크린리더 전용 텍스트(`sr-only` 등)는 화면에 안 보여도 읽히므로 지우지 않는다. 팝업 모드(`--popup-layer`)에서는 `role="dialog"`와 modal·popup class·id 규칙을 끈다.
4. 요소 순회 + 텍스트 수집: 남은 HTML 요소를 순회하며 카테고리로 분류하고 텍스트를 수집한다. `nav`, `footer`, `header`(그리고 role이 navigation, banner, contentinfo인 요소) 내부는 반복 메뉴·저작권 표시이므로 건너뛴다. `div`, `section` 같은 컨테이너는 자식 블록 요소가 있으면 직접 텍스트만 수집하고, "카테고리:텍스트"가 같은 블록은 한 번만 남긴다. 두 글자 미만은 버린다.
5. form_guide 별도 추출: `placeholder`, `aria-label`, `title` 속성값은 태그의 텍스트 노드가 아닌 속성에 들어 있으므로 별도로 추출한다(페이지 `<title>`은 제외). `title`·`aria-label`이 그 요소에 보이는 글을 그대로 담고 있으면(예: `<a title="공고 제목 게시물로 이동">공고 제목</a>`) `attributes.duplicates_visible_text = true`를 붙인다(2026-10-02). 난이도 엔진은 이 블록의 글자 수 검사를 건너뛴다(같은 제목이 link와 form_guide로 두 번 감점되지 않도록).

출력 JSON 구조:

```json
{
  "meta": {
    "total_blocks": 413,
    "total_sentences": 414,
    "categories": { "paragraph": 135, "form_guide": 134, "link": 85 }
  },
  "blocks": [
    {
      "text": "급한 생활비, 대출 연체...",
      "category": "paragraph",
      "tag": "p",
      "selector": "html > body > main > section > p",
      "attributes": { "id": "...", "class": "..." },
      "sentences": ["급한 생활비, 대출 연체..."]
    }
  ]
}
```

`form_guide` 블록의 `attributes`에는 `source`(placeholder, aria-label, title 중 어디서 왔는지)와, 해당될 때 `duplicates_visible_text: true`가 들어간다. 문장은 마침표·물음표·느낌표 뒤 공백에서 나누는 간이 규칙으로 자르고, 소수점("3.5%", "2026.06.22")에서는 자르지 않는다.

### difficulty_engine.py — 한국어 인지 난이도 분석 엔진

**입력:** `result_text.json`  
**출력:** `result_text_difficulty.json`

text_extractor.py가 분류한 텍스트 블록을 카테고리별로 분석하여 인지 난이도 점수를 산출한다. 기존 도구(WAVE, Lighthouse)가 코드 구조만 검사하는 것과 달리, 이 엔진은 **콘텐츠 자체의 인지적 어려움**을 측정한다.

**종합 점수 산출 — Jo(2016) 국어 이독성 공식 기반**

paragraph 블록에는 아래 공식을 적용하여 학년 수준(GL)을 산출한다.

```
GL = 4.874 + 0.591 × A − 9.201 × B³

A = 평균 문장 길이 (어절 수)  → 길수록 어려움
B = 쉬운 단어 비율 (국립국어원 A+B등급과 웹 인터페이스 어휘 W의 일반명사 / 전체 일반명사)  → 높을수록 쉬움
    고유명사(NNP)는 2026-10-02부터 세지 않는다. 일반명사가 5개 미만이면 B와 GL을 계산하지 않는다.
    문장 끝 부호(. ? !)가 하나도 없는 문단에는 공식을 쓰지 않는다(2026-10-04).
```

2026-09-27 수정: 예전 코드는 A 항의 부호가 `−`로 원 논문과 반대였다. 그래서 문장이 길수록 쉽다고 계산됐고, 평균 문장 길이가 약 6.55어절을 넘으면 난이도 점수가 항상 0이 되어 최댓값이 약 35.2점에 묶여 있었다. 원식대로 `+`로 고쳤다.

출처: 조용구(2016). 글의 수준을 평가하는 국어 이독성 공식. 독서연구 제41호, pp.71-91.  
논문의 공식 구조를 채택하되, 어휘 목록은 국립국어원 학습용 어휘 등급(A/B/C, 5543개)으로 대체하여 공공 웹 콘텐츠 도메인에 맞게 적용했다. A+B등급(2888개)을 쉬운 단어로 정의한다.

GL은 아래 공식으로 0~100 난이도 점수로 변환된다.

```
difficulty_score = clip((GL − 1) / 11 × 100, 0, 100)      GL 1 → 0점, GL 12 → 100점
수정 제안 기준   = difficulty_score 72.7 이상 (= GL 9)

page_score = max(0, 100 − (공식을 적용한 paragraph의 difficulty_score 평균))     (2026-10-13)
             평균에는 다른 공식 문단을 품지 않은 가장 안쪽 문단만 넣는다 (2026-10-09)
```

`page_score`는 run_all.py가 텍스트 모듈 점수로 쓴다. `difficulty_score_v2`와 명사 나열은 여기에 들어가지 않는다(아래).

**2026-10-13에 뺀 감점.** 예전 식은 여기서 위치 의존 감점(건당 3점, 최대 15점)과 UI 텍스트 길이 감점(건당 2점, 최대 20점)을 더 뺐다. 위치 의존은 10개 사이트 2,822블록에서 진짜 사례가 0건이었고 패턴이 과녁을 벗어났으며(아래), 길이 감점은 큰 사이트에서 늘 상한 20점에 닿아 사이트를 가르지 못했고 기준(20~60자)에 근거가 없었다. 두 검사의 플래그와 수정 제안은 그대로 내고, `meta.score_breakdown`에는 `scored_paragraphs`(평균에 들어간 문단 수), `avg_difficulty_deduction`(문단 평균), 참고용 `sensory_instruction_texts`(감각 의존 지시가 있는 글 수, 같은 글은 한 번)와 `ui_length_flags`만 남는다. `meta.page_score_formula`에 식을 적는다. 같은 본문(9/14 추출본)으로 다시 채점하면 서울시 50.2 → 70.2, 국민건강보험공단 5.4 → 25.4, 보건복지부 40.2 → 50.9(10/9 중복 제거 포함), 봉화군청 0.0 → 15.8이고 홈택스·정부24 등본은 같다.

**기준을 넘은 문단의 목표값 (2026-10-13).** 난이도 72.7 이상인 문단에는 기준식(GL = 9)을 거꾸로 풀어 `metrics.gl_targets`를 붙인다.

```
max_avg_sentence_length = (9 − 4.874 + 9.201 × B³) / 0.591          (쉬운 단어 비율은 그대로 둘 때)
min_easy_word_ratio     = ((4.874 + 0.591 × A − 9) / 9.201) ^ (1/3)  (문장 길이는 그대로 둘 때)
```

예: 평균 12어절, 쉬운 단어 45%(난이도 92.1점) → "평균 8.4어절 이하 또는 쉬운 단어 68.6% 이상". 평균이 약 22.6어절을 넘으면 어휘를 모두 쉬운 말로 바꿔도 GL 9 아래로 못 가므로 `min_easy_word_ratio`가 `null`이다. 고정된 "60%" 대신 이 글에 맞는 목표를 수정 안내에 쓴다. 판정·점수는 바뀌지 않는다.

**감각 의존 지시 탐지 (2026-10-13, `detect_sensory_instructions`)**

WCAG 1.3.3 감각적 특성(KWCAG 5.3.3 명확한 지시사항 제공)은 모양·색·크기·위치·방향·소리 같은 감각 정보"에만" 기대어 대상을 가리키는 안내를 문제로 본다. 아래 세 조건이 **한 문장에 함께** 있을 때만 `감각 의존 지시(위치|색|모양|소리): "인용(30자 이내)" — 이유` 플래그를 붙인다(종류마다 한 번).

| 조건 | 내용 |
|---|---|
| (1) 감각 단서 | 위치: 오른쪽·왼쪽·우측·좌측·옆·우상단·좌하단 등, "화면/페이지/창 + 상단·하단·위·아래". 색: 빨간색·파란·초록·회색 등 색 이름. 모양: 동그란·둥근·네모난·세모·"○○ 모양". 소리: "삐 소리가 나면", "신호음이 들리면" 등 |
| (2) 이름 없는 일반 대상에 바로 붙음 | 단서 바로 뒤에 버튼·아이콘·메뉴·링크·탭·창·표·그림·항목·영역·글자 같은 일반 낱말이 온다. 사이에는 상단·의·에서·있는·위치한·표시된·큰·작은·색 수식어·"두 번째" 같은 말만 허용하고, 대상의 이름이 끼면 걸리지 않는다("오른쪽 '로그인' 버튼", "오른쪽 로그인 버튼"). 대상 낱말 뒤에 따옴표·괄호로 이름이 붙어도 걸리지 않는다 |
| (3) 조작·확인 지시 | 대상 낱말 뒤 40자 안, 같은 문장에 누르·클릭·터치·선택·이용·확인·참고·입력·찾·"하세요"·"바랍니다" 같은 말. 소리는 누르·말씀·녹음·시작 같은 말 |

| 예 | 결과 | 이유 |
|---|---|---|
| "오른쪽 버튼을 클릭하세요" | 감각 의존 지시(위치), high | 이름 없이 위치만 |
| "빨간색 버튼을 누르면 삭제됩니다" | 감각 의존 지시(색), high | 이름 없이 색만 |
| "동그란 아이콘을 누르세요" | 감각 의존 지시(모양), high | |
| "삐 소리가 나면 말씀하세요" | 감각 의존 지시(소리), high | 소리 신호에만 의존 |
| "화면 아래의 버튼을 누르세요" | 감각 의존 지시(위치), medium | 화면 전체 기준 위·아래 |
| "오른쪽 상단의 '로그인' 버튼을 누르세요" | 없음 | 이름을 함께 씀(기법 G96) |
| "위의 표를 참고하세요", "아래 버튼을 눌러 신청하세요" | 없음 | 읽는 순서상 참조. 스크린리더도 같은 순서로 읽는다 |
| "마우스 오른쪽 버튼", "오른쪽 방향키" | 없음 | 화면 위치가 아니라 장치 이름 |
| "왼쪽 메뉴 닫기", "왼쪽 사진은 ○○ 의원" | 없음 | 버튼 이름·설명(지시 없음) |
| "2위", "좌측통행", "오른쪽 창문" | 없음 | 다른 뜻의 낱말 |

- **정밀도 우선.** 세 조건을 모두 요구하므로 놓치는 문장이 있다(색으로만 뜻을 전하는 설명 "빨간색으로 표시된 항목은 필수입니다" 등). 설문 쌍 116개 글에서 오탐 0건, 손으로 만든 시험 문장 47개, 10개 사이트 메인 페이지 2,822블록(9/14 추출본)에서 0건(오탐 0, 진짜 사례도 없음). 이용 안내·FAQ처럼 지시문이 많은 페이지의 재현율은 아직 모른다.
- **같은 글 한 번.** 한 문장이 목록·링크·문단 블록에 겹쳐 추출되면 블록마다 플래그가 붙으므로, 페이지 단위로 셀 때는 다른 플래그 글을 품지 않은 가장 안쪽 글만 센다(`count_flagged_texts`, `score_breakdown.sensory_instruction_texts`).
- **모호한 참조는 그대로.** `해당 (버튼|메뉴|링크|항목|페이지)`, `(여기|이곳)를? 클릭`은 `모호한 참조` 플래그(WCAG 2.4.4 → KWCAG 6.4.3, medium). 링크 글자 자체가 "여기"·"더보기"뿐인 경우는 규칙 모듈 `link-audit.js`가 6.4.3으로 감점한다. 두 탐지를 합친 함수가 `detect_reference_flags()`이고, 옛 이름 `detect_location_dependency`도 같은 함수를 가리킨다.
- **옛 결과 호환.** 2026-10-13 전 결과의 `위치 참조: "위" 사용` 같은 플래그도 `text_standard_mapper.py`와 수정 제안이 그대로 처리한다(`location_dependency`, 좌우·옆 high, 위·아래 medium).

**바꾼 이유 (2026-10-13).** 10/3까지의 "위치 참조"는 `위의? `, `아래의? `, `오른쪽`·`왼쪽`·`우측`·`좌측`·`옆` 같은 낱말이 문장에 있기만 하면 걸고 글당 3점(최대 15점)을 깎았다. 10개 사이트 2,822블록에서 진짜 사례는 0건이었고(10/2 수정 전 2건은 "박스오피스 2위 하락" 오탐), 넓혀 찾아봐도 "페이지 상단으로 이동" 같은 건너뛰기 링크와 고유명사뿐이었다. 더 큰 문제는 과녁이었다. WCAG 해설서는 읽는 순서상 위·아래 참조("아래 링크 중 하나를 고르세요")를 충족 사례로 들고, 이름을 같이 쓴 위치 표현도 기준을 지킨 것이다. 반대로 1.3.3이 실제로 말하는 색·모양·소리 지시는 낱말 목록에 없었다. 3점이라는 값에도 근거가 없었다. 그래서 탐지 조건을 위처럼 좁히고 페이지 점수에서 뺐다. 점수에 다시 넣으려면 오탐률과 놓친 비율을 사람 판정과 맞춰 본 뒤에 정한다.

**카테고리별 분석 수준**

| 카테고리 | 적용 분석 |
|---|---|
| paragraph | 일반명사 5개 이상이고 문장 끝 부호가 있으면 Jo(2016) 공식 전체(긴 글). 명사 5개 이상인데 부호가 없으면(메뉴·게시판 목록 덩어리) 공식도 어휘 검사도 하지 않고 `metrics.jo_skipped = "no_sentence_terminator"`만 남김(2026-10-04). 명사 5개 미만이면 어려운 단어(C·D등급, 웹 인터페이스 어휘 제외) 2개 이상일 때 보조 플래그(짧은 글). 모두 감각 의존 지시 탐지. 고유명사(NNP)는 세지 않음. 플래그가 하나라도 있으면 수정 제안 대상(기준 72.7 이상인 문단은 항상 원인 플래그나 "읽기 수준 초과"를 받음) |
| button / link / label / form_guide / heading | 텍스트 길이 기준(20/30/40/50/60자, 참고 기준) + 감각 의존 지시 탐지. 보이는 글을 그대로 담은 title·aria-label은 길이 검사 제외 |
| table / list / alert / other | 평균 문장 길이(문장 끝 부호가 있는 글만) + 감각 의존 지시 탐지(2026-10-02 추가) |
| 모든 카테고리 | 명사 나열 (문장 끝 부호가 있는 글만) |

UI 문구(button·link·label·form_guide·heading)와 table·list·alert·other에는 어휘 검사를 하지 않는다. 짧은 문단과 같은 "어려운 단어 2개 이상" 규칙을 UI 문구에 적용해 보면 10개 사이트 UI 문구 1,381개 중 620개(45%)가 걸리고(C등급 2개 이상으로 좁혀도 169개), "검색어를 입력해 주세요", "학부모게시판" 같은 오탐이 많았다. 학습용 어휘 목록이 "입력", "게시판", "안내"를 고급(C) 단어로 보기 때문이다. 대신 모든 블록의 `metrics.hard_noun_count`에 개수를 기록해 두고, 어휘 목록을 바꾸거나 2차 설문 뒤 다시 판단한다.

**긴 글과 짧은 글 (2026-10-04 정리).** 이 모듈의 평가는 공식을 쓸 수 있는 "긴 글"(문장 끝 부호가 있고 일반명사 5개 이상인 문단)과 그렇지 않은 "짧은 글"로 나뉜다.

| | 긴 글 | 짧은 글 |
|---|---|---|
| 대상 | 문장으로 쓰인 문단 | 짧은 문단, UI 문구, 표·목록 조각, 부호 없는 목록 덩어리 |
| 평가 요소 | Jo 공식(문장 길이 + 쉬운 단어 비율 → GL, 기준 GL 9), 원인 표시(문장 길이 25어절·쉬운 단어 60%·읽기 수준 초과), GL 목표값, 명사 나열, 감각 의존 지시 | 짧은 문단은 어려운 단어 2개 이상, UI 문구는 글자 수, 조각 글은 문장 부호가 있을 때만 문장 길이·명사 나열. 모두 감각 의존 지시 |
| 10개 사이트 블록 수 | 47 | 2,775 |

짧은 글은 글 자체가 짧아 잴 수 있는 것이 사실상 "어떤 단어를 썼나" 하나다. 문장 구조(길이·명사 나열)는 문장이 있어야 의미가 있고, 짧은 글 대부분은 문장 끝 부호가 없는 이름·제목이다. 그래서 짧은 글은 어휘 수준으로만 평가하고, 이 평가의 정확도를 올리는 쪽(웹 인터페이스 어휘, 아래)에 집중했다. 공공기관 제목은 원래 명사로 끝나는 개조식이 표준이라 부호 없는 글에 명사 나열 검사를 넣으면 거의 다 걸리므로 넣지 않았다.

짧은 글에 Jo 공식을 쓰지 않는 것은 짧은 글이 쉬워서가 아니라 공식으로 잴 수 없어서다. 문장이 끝나지 않는 조각 글은 평균 문장 길이가 의미가 없고, 명사가 적으면 쉬운 단어 비율이 한 단어에 크게 흔들린다. 1차 설문에서 가장 어렵다고 평가된 두 글은 오히려 평균 문장 길이 3.5·4.3어절로 가장 짧은 편이었다.

| 쉬운 단어 비율 최솟값 | 60% | 자체 설계값(근거 없음). 설문 후보 58쌍에서 쉽게 고친 수정문도 54개 중 40개(74%)가 60% 미만이라(원문 84%) 원문과 거의 구분하지 못함. 그래서 단독 위반으로 쓰지 않고, 난이도 점수가 기준을 넘은 문단의 원인 설명으로만 붙임. 2026-10-13부터 수정 안내에는 이 고정값 대신 식에서 역산한 목표(`gl_targets`)를 쓴다 |
| UI 글자 수 | 20/30/40/50/60자 | 근거 없음(경험값). 링크 30자는 "링크 글은 구체적이어야 한다"는 WCAG 2.4.4와 방향이 반대라, 30자 넘는 링크 대부분이 뉴스·공지 제목이다. 2026-10-13부터 점수에 안 쓰고 "참고 기준"으로만 안내 |

이 숫자들이 한 식(GL = 4.874 + 0.591A − 9.201B³)에 묶여 있다는 점도 알아 둔다. A가 25어절이면 B가 1이어도 GL이 10.45라, 공식 문단에서 25어절 플래그는 판정을 바꾸지 않고 원인만 설명한다. 1어절은 난이도 약 5.4점이고, 쉬운 단어 비율 0.4 → 0.6은 약 12.7점이다. 학습용 어휘 목록 탓에 B가 0.4 안팎으로 낮게 잡히므로 사실상 문장 길이가 점수를 움직이며, 눈금 전체를 정하는 진짜 손잡이는 어휘 목록이다. 목록 교체는 2차 설문을 검증으로 남기기 위해 다음 탐색에서 한다.
| 고유명사 제외 | NNP 제외 | WCAG 2.2 3.1.5가 "고유명사와 제목을 제거한 뒤" 읽기 수준을 판단하라고 명시 |
| 문장 끝 부호 (10/4 추가) | 공식 적용 조건 | 문장 길이 플래그와 같은 조건. 부호 없는 글은 블록 전체가 한 문장으로 계산돼 A가 의미 없음. 10개 사이트 공식 적용 문단 148개 중 101개가 부호 없는 메뉴·게시판 목록이었고 기준 초과 55개 중 31개를 차지 |
| 웹 인터페이스 어휘 (10/4 추가) | 55개를 쉬운 단어(W)로 | 누리집 기능·화면 요소 이름(입력, 검색, 로그인, 게시판, 안내 등). 학습용 목록에서 C·D지만 사이트를 쓰는 것만으로 접하는 말. 기준은 빈도가 아니라 "사이트 기능의 이름인가"(공공기관 전문 용어가 섞여 들어오지 않게) |
| 짧은 문단 어려운 단어 수 | 2개 이상 | 1개 기준은 짧은 문단의 62%에 붙었고 "검색", "유튜브" 같은 흔한 말이 대부분이었음. 코드에 미리 적어 둔 "과탐지가 많으면 2 이상으로" 규칙을 적용 |
| UI 텍스트 길이 | 20/30/40/50/60자 | 근거 자료 없음(경험값). 30자 넘는 링크 대부분이 뉴스·공지 제목이라 재검토 필요 |
| 명사 나열 | 명사로만 된 어절 4개 연속 | 문화체육관광부·국어문화원연합회 "쉬운 우리말 쓰기"(2020)가 명사 나열 문장을 이해하기 어려운 표현으로 꼽고, 조사·서술어를 넣어 풀어 쓰라고 권함. 기준 4는 캠페인 예시 "사후 평가 결과 반영"의 길이 |

모든 카테고리에서 "플래그가 있음"과 `needs_suggestion`(수정 제안 필요)이 같다. 플래그마다 `standard_issues`에 WCAG·KWCAG 항목이 붙어 백엔드가 그대로 저장한다.

**2026-10-04 재분석 (문장 끝 부호 조건 + 웹 인터페이스 어휘).** 같은 10개 사이트에서 공식을 적용한 문단이 148개에서 47개로, 기준(72.7)을 넘는 문단이 55개에서 23개로, 수정 제안 대상 블록이 308개에서 234개로 줄었다. 부호 조건만으로 148→47, 55→24, 308→277이고 나머지는 어휘 목록 효과다. 짧은 문단 "어려운 어휘 포함"은 127건에서 85건, "어려운 어휘 과다"는 49건에서 20건이 됐다. 무작위 표본으로 본 짧은 문단 플래그의 정확도(Claude가 표본을 읽고 판단한 값)는 20개 중 4~5개에서 25개 중 10~12개(약 45%)로 올랐다. 남은 오탐은 "레시피", "썸네일", "키보드" 같은 외래어와 MeCab이 고유명사로 못 잡은 이름이다. 설문 원문·수정문 53쌍(점수가 나오는 쌍)의 구분력은 그대로 유지됐다(원문 평균 83.9 → 82.2점, 수정문 66.9 → 65.4점, Wilcoxon p<0.001, Youden J 72.7 기준 0.28 → 0.30). `compute_pair_difficulty.py`는 설문 글에 공식을 직접 적용하므로 문장 끝 부호 조건은 쓰지 않는다.

페이지 점수(`page_score`)는 크게 움직였다. 공식 대상 문단이 줄어 문단 평균이 몇 개 문단으로 정해지기 때문이다. 정선군청은 공식 대상 문단이 0개가 되어 25.9점에서 98.0점, 보건복지부 11.5 → 40.2, 서울시 26.4 → 50.2, 네이버 27.9 → 45.7, 위례별초 36.8 → 54.2, 국민건강보험공단 13.4 → 5.4, 홈택스 44.2 → 32.0이고 봉화군청(0점)과 정부24 등본·초본(16.6)은 그대로다. 예전 점수는 메뉴 덩어리의 가짜 난이도가 끌어내린 값이라 맞는 값이 아니었고, 지금 점수는 "평가할 문장이 적은 페이지는 높게 나온다"는 기존 한계(글이 없으면 100점)를 더 드러낸다.

10개 사이트(9/14 실행 9곳 + 9/28 네이버) 재분석 결과(10/2), 수정 제안 대상 블록이 609개에서 301개로(이후 명사 나열 추가로 308개, 그중 6개는 "읽기 수준 초과"), 기준을 넘는 문단이 90%(149/165)에서 36%(55/151)로 줄었다. 문장 길이 플래그는 8건에서 2건(실제 긴 문장 1건, "공유재산이란?"이 섞인 메뉴 덩어리 1건)으로, 위치 참조는 2건("2위 하락")에서 0건으로, form_guide 길이 위반은 10건에서 3건으로 줄었다.

**명사 나열 지표와 종합 난이도 v2 (2026-10-02 추가, 검증 전)**

1차 설문(폼1 22개 글)의 체감 난이도와 순위 상관을 지표별로 탐색해, 체감 난이도와 같은 방향으로 움직이는 지표를 엔진에 더했다.

- `metrics.noun_eojeol_run`: 조사·어미 없이 명사류로만 된 어절이 가장 길게 이어진 개수. 글 전체를 한 번에 형태소 분석한 뒤 어절별로 나눠 센다. 쉼표·괄호 같은 문장부호가 든 어절, 숫자·로마자가 든 어절에서 끊고, 붙여 쓴 합성어("건강보험료")는 1개로 센다.
- `metrics.hard_noun_count`: 어려운 일반명사(C·D등급) 개수. 비율과 달리 짧은 글에서 왜곡되지 않는 참고 지표.
- `difficulty_score_v2` = (Jo 난이도 점수 + 명사 나열 점수) / 2. 명사 나열 점수는 1어절 0점, 4어절 50점, 7어절 이상 100점. 두 하위 점수를 같은 비중으로 더한 이유는, 22개 글로 가중치를 맞추면 그 22개에만 맞는 값이 나오기 때문이다(같은 비중이 작은 표본에서 더 안정적이라는 Dawes, 1979).
- `meta.readability.avg_difficulty_v2`: 문단 v2 평균.

1차 설문 탐색 결과 (같은 20개 글 기준, Spearman):

| 지표 | ρ | p |
|---|---|---|
| Jo 난이도 점수 (기존) | 0.06 | 0.80 |
| 글자 수 (비교 기준) | 0.15 | 0.53 |
| 명사 나열 길이 | 0.30 | 0.19 |
| **종합 난이도 v2** | **0.30** | 0.19 |
| 어려운 단어 개수 (참고, v2에 미포함) | 0.47 | 0.04 |

원문·수정문 58쌍에서는 명사 나열 4어절 이상이 원문 23개, 수정문 2개였고, v2 평균은 원문 58.8점, 수정문 39.8점이었다(Wilcoxon p<0.001).

**주의:** 이 22개 글은 지표를 고르는 데 쓴 탐색 자료이고 모두 링크·안내 문구 조각이다. 여기서 나온 상관은 증명이 아니다. 그래서 검증 전까지 페이지 점수와 "수정 제안 필요" 판정은 기존 Jo 점수를 그대로 쓰고, v2는 결과에 기록만 한다. 명사 나열 플래그는 수정 제안만 붙고 감점은 없다.

**2차 설문 검증 계획** (10/2 고정, 10/4 응답 수집 전 수정. 아래 "2차 설문" 절)

10개 사이트에서 명사 나열 플래그는 17건 붙었다. 국민건강보험공단의 "소득 부과 건강보험료 조정 정산 제도"(7어절) 같은 실제 사례와 함께, `div`로 만든 메뉴 덩어리(봉화군청, 홈택스)도 2건 걸렸다. 메뉴를 문단으로 추출하는 쪽의 문제다.

**알려진 한계**
- 쉬운 단어 목록인 국립국어원 학습용 어휘(2003)는 외국인 학습자용이다. "가능", "지원"이 C등급, "정책", "확대"가 목록 밖(D)이라 한국어 모어 화자 기준으로는 어려운 단어가 과대 추정된다. 10개 사이트 문단 명사의 약 42%가 목록 밖이었다. 2026-10-04에 누리집 기능 이름 55개("안내", "검색", "입력" 등)만 쉬운 단어로 바꿨고, 일상 어휘 전반은 그대로다.
- 공식이 적용되는 문장도 15어절쯤부터 GL이 12를 넘어 100점에 붙는다("분천 산타마을은 국내 최초 산타 테마로…" 17어절, 100점). 어휘 목록 탓에 쉬운 단어 비율이 0.4 안팎으로 낮게 잡히기 때문이다. 기준을 넘은 문단끼리는 어느 쪽이 더 어려운지 구분하지 못한다. 문단 단위 사람 평가(2차 설문)로 맞출 과제다.
- 문장 끝 부호 조건은 휴리스틱이다. 메뉴 덩어리 안에 마침표가 하나라도 있으면 공식이 적용된다(10개 사이트에 2건 남음: 봉화군청 관련기관 목록, 홈택스 관련 사이트 목록).
- 페이지 점수(`100 − 긴 글 난이도 평균`)는 쉽다고 평가된 수정문도 난이도 점수가 평균 65점대라 긴 글이 많은 페이지는 낮게 나오고, 긴 글이 없거나 적은 페이지는 높게 나온다(정선군청·정부24 대표·홍익대는 긴 글 0개라 100점, `scored_paragraphs`가 0). 긴 글이 적으면 "측정 불가"로 둘지 검토가 남아 있다(`run_all.py`·백엔드·대시보드를 같이 바꿔야 함).

### suggestion_generator.py — 수정 제안 생성기

**입력:** `result_text_difficulty.json`  
**출력:** `result_text_suggestions.json`

difficulty_engine.py가 위반으로 판정한 블록들에 대해 수정 가이드를 자동 생성한다. 두 가지 방식을 병행한다.

**방식 1 — 규칙 기반 템플릿 (항상 동작)**

플래그 유형별로 미리 작성된 수정 가이드를 반환한다. OpenAI API 키 없이도 동작하며, LLM 호출이 활성화된 경우에도 함께 제공된다.

| 플래그 유형 | 제안 내용 | 저장되는 표준 참조 |
|---|---|---|
| 문장 길이 과다 | 접속사로 이어진 문장을 마침표로 분리 + GL 9 목표(평균 몇 어절 이하, 2026-10-13) | WCAG 3.1.5 읽기 수준 (KWCAG 직접 대응 없음) |
| 어려운 어휘 과다 | C/D등급 어휘 목록 제시 + 쉬운 단어 대체 예시 + GL 9 목표(쉬운 단어 몇 % 이상 또는 평균 몇 어절 이하) | WCAG 3.1.5 읽기 수준 (KWCAG 직접 대응 없음) |
| 어려운 어휘 포함(표본 부족) | 짧은 문단의 어려운 단어 목록 + 일상어로 바꾸기 | WCAG 3.1.5 읽기 수준 (2026-10-02 매핑 추가. 예전에는 기준 번호 없이 KWCAG에 없는 "3.1.1"이 적혀 있었음) |
| 감각 의존 지시 (2026-10-13) | 감각 정보에 대상의 이름을 함께 쓰기. 위치: "오른쪽 버튼을 클릭하세요" → "오른쪽의 '제출' 버튼을 클릭하세요". 색: "빨간색 버튼" → "'삭제' 버튼(빨간색)". 모양: "동그란 아이콘" → "'검색' 아이콘(돋보기 모양)". 소리: 같은 내용을 화면 글로도("삐 소리가 나고 화면에 '녹음 중'이 표시되면"). 우선순위 좌우·옆·색·모양·소리 high, 화면 위·아래 medium | WCAG 1.3.3 → KWCAG 5.3.3 명확한 지시사항 제공 (`sensory_instruction`) |
| 위치 참조 (2026-10-13 전 결과 호환) | 위치 대신 대상의 이름 쓰기. 우선순위 좌우·옆 high, 위·아래 medium | WCAG 1.3.3 → KWCAG 5.3.3 (`location_dependency`) |
| 모호한 참조 (2026-10-03 분리) | "해당"·"여기" 대신 대상의 이름 쓰기 ("여기를 클릭하세요" → "'민원 신청' 페이지로 이동하세요"), 우선순위 medium | WCAG 2.4.4 → KWCAG 6.4.3 적절한 링크 텍스트 |

| 버튼 텍스트 길이 초과 | 동작을 2~4단어로 표현 | WCAG 2.4.4 → KWCAG 6.4.3 적절한 링크 텍스트 |
| form_guide·label 길이 초과 | 자세한 설명은 별도 안내 텍스트로 분리 | WCAG 3.3.2 → KWCAG 7.3.2 레이블 제공 |
| heading 길이 초과 | 제목을 간결하게 요약 | WCAG 2.4.6 → KWCAG 6.4.2 제목 제공 |
| 명사 나열 (10/2 추가) | 명사 사이에 조사·서술어를 넣어 풀어 쓰기 ("사후 평가 결과 반영" → "사후 평가 결과를 반영하여") | WCAG 3.1.5 읽기 수준 (KWCAG 직접 대응 없음) |
| 읽기 수준 초과 (10/2 점검에서 추가) | 긴 문장을 마침표로 나누고, 마침표 없이 이어 붙인 제목·날짜·설명은 줄을 나누거나 문장으로 정리 + GL 9 목표 | WCAG 3.1.5 읽기 수준 (KWCAG 직접 대응 없음) |

GL 9 목표 문장 예: "기준(GL 9)을 맞추려면 쉬운 단어 비율은 그대로 두고 평균 문장 길이를 8.4어절 이하로 줄이거나(지금 12.0어절), 문장 길이는 그대로 두고 쉬운 단어 비율을 68.6% 이상으로 올려야 합니다(지금 45.0%). 둘을 섞어 맞춰도 됩니다." 목표값이 없는 옛 결과는 예전 문장 그대로다.

**방식 2 — LLM 수정 제안 (OpenAI GPT API, 조건부)**

난이도 엔진의 측정 수치(평균 문장 길이, 어휘 등급 상세, 종합 난이도 점수)를 프롬프트에 포함하여 원문을 실제로 쉽게 다시 쓴 수정문과 수정 이유를 생성한다.

측정은 자체 엔진이 수행하고, LLM은 분석 결과를 바탕으로 수정안만 제시하는 역할 분담이 핵심이다.

**LLM 호출 대상 및 비용 관리**

| 조건 | 대상 |
|---|---|
| paragraph이고 난이도 점수 50 이상 | LLM 호출 (2026-10-02부터 수정 제안 기준이 72.7이라, 50~72점 문단은 감각 의존 지시·명사 나열로 수정 제안 대상이 됐을 때만 해당) |
| link 또는 form_guide이고 텍스트 40자 이상 | LLM 호출 |
| 그 외 | 규칙 기반 제안만 제공 |
| 최대 호출 수 | 20건/실행 (MAX_LLM_CALLS, 실패한 호출 포함) |
| 동시 호출과 시간 예산 | 4건씩 동시에(LLM_CONCURRENCY), 전체 80초 안에서만(LLM_TIME_BUDGET_SECONDS). run_all.py의 단계 제한 시간 120초 안에 끝내기 위해서 |
| 사용 모델 | gpt-4o-mini (temperature 0.3, max_tokens 500, 실패 시 2번 재시도) |
| STUDY_MODE=1 | 설문용 원문·수정문 쌍을 모을 때 위 조건을 풀고 최대 60건까지 호출 |

출력 블록에는 `standard_issues`, `suggestions`(유형, 문제, 가이드, `wcag_ref`, `kwcag_items`, 우선순위), `llm_revision`(수정문, 이유, 모델명, 안 불렀거나 실패하면 null)이 붙는다. `meta.suggestion_stats`에 제안 수와 LLM 호출·성공 건수가 기록된다.

LLM 프롬프트는 2026-10-13에 바꾸지 않았다. 감각 의존 지시나 GL 목표를 넣으면 수정문이 나아질 수 있지만, 오프라인에서 검증할 방법이 없어 후속 과제로 둔다.

### korean_vocab_grades.json — 국립국어원 학습용 어휘 등급 사전

difficulty_engine.py의 쉬운 단어 비율(B 변수) 계산에 사용되는 어휘 목록이다.

등급은 학교 학년이 아니라 한국어 학습자(주로 외국인)의 학습 단계다.

| 등급 | 수준 | 어휘 수 | 엔진에서의 취급 |
|---|---|---|---|
| A | 초급 | 894개 | 쉬운 단어 |
| B | 중급 | 1,994개 | 쉬운 단어 |
| C | 고급 | 2,655개 | 어려운 단어 |
| D | 목록에 없음 (코드상 표기) | - | 어려운 단어 (행정·전문 용어 대부분) |
| W | 웹 인터페이스 어휘 (`web_common_words.json`, 2026-10-04) | 55개 | 쉬운 단어. 원래 C·D인 누리집 기능 이름만 |

### web_common_words.json — 웹 인터페이스 어휘 (2026-10-04)

짧은 글 어려운 단어 플래그의 오탐 대부분("로그인 회원가입", "기관 검색 전체보기", "챗봇", "컨트롤로 돌아가기")은 학습용 목록이 누리집 기능 이름을 어렵게 보기 때문이었다. 그래서 원래 C·D등급인 말 중 **누리집의 화면 요소·기능 이름**만 골라 `get_word_grade()`가 'W'를 돌려주게 했다. 'W'는 A·B와 같이 쉬운 단어(`EASY_GRADES`)로 세므로 Jo 공식의 B, 짧은 문단 판정, 수정 제안·LLM 프롬프트의 어려운 단어 목록에 모두 같이 반영된다.

| 분류 | 단어 |
|---|---|
| 화면 구성 (19) | 화면, 페이지, 본문, 상단, 하단, 창, 새창, 팝업, 슬라이드, 목록, 게시판, 게시물, 자료실, 주메뉴, 사이트, 맵, 링크, 홈, 컨트롤 |
| 기능·동작 (19) | 입력, 검색, 검색어, 열기, 열림, 가입, 로그인, 로그아웃, 접속, 설치, 설정, 공유, 구독, 다운로드, 업로드, 첨부, 클릭, 조회, 댓글 |
| 공통 메뉴 이름 (4) | 안내, 문의, 공지, 사항 |
| 서비스·매체 (13) | 누리집, 웹, 온라인, 앱, 블로그, 동영상, 이메일, 브라우저, 콘텐츠, 아이디, 비밀번호, 챗, 봇 |

- **고른 기준은 "자주 나오는가"가 아니라 "사이트 기능의 이름인가"다.** 10개 사이트가 대부분 공공기관이라 빈도로만 고르면 4곳 이상에 나오는 C·D 단어 59개에 민원, 행정, 입찰, 법령, 채용, 보건, 복지, 소득 같은 공공기관 내용 어휘가 같이 들어온다. 내용 어휘는 이 모듈이 잡아야 할 대상이므로 넣지 않았다.
- MeCab이 합성어를 쪼개므로 "챗봇"은 챗+봇, "공지사항"은 공지+사항, "사이트맵"은 사이트+맵으로 들어 있다. "사항"은 "공지사항" 때문에 넣었고 "유의사항" 같은 말에도 쉬운 단어로 적용된다.
- 원래 A·B등급인 말(메뉴, 홈페이지, 회원, 파일, 버튼, 인터넷)은 이미 쉬운 단어라 넣지 않았다. "모바일", "배너"는 MeCab이 고유명사(NNP)로 봐서 원래 세지 않는다.
- 각 단어에 원래 등급과 10개 사이트 중 몇 곳에 나왔는지(`sites_of_10`)를 함께 적어 두었다. 단어 선정은 사람이 판단한 목록이라 팀에서 한 번 검토하는 것이 좋다.

## 2차 설문: 엔진 점수가 체감 난이도와 맞는지 검증

이 모듈의 핵심 검증이다. 1차 설문은 원문·수정문 쌍으로 "AI 수정문이 더 쉽다"(59명, d=1.05)는 것을 보였지만, 글이 링크·폼 안내 조각이라 엔진 점수와 체감의 글 단위 상관은 확인하지 못했다. 짧은 글은 공식을 쓰지 않으므로, 2차 설문은 공식을 적용하는 **긴 글**만 다룬다.

| 항목 | 내용 |
|---|---|
| 대상 | 공공기관 본문 페이지(공지 본문, 제도 안내, 민원 신청 방법)의 긴 글. 엔진이 공식을 적용한 문단, 40~250자, 문장 1~3개 |
| 뽑는 법 | GL 원값 구간 5개(5 미만 / 5~7 / 7~9 / 9~12 / 12 이상)에서 6개씩 = 30개. 구간 안에서 짧은 글(120자 이하)과 긴 글을 반씩, 사이트를 돌아가며. 폼 공통 글 2개(5~7, 9~12 구간) 따로 = 총 32개. 모자란 구간은 다른 구간으로 채우지 않고 사이트를 더 돌린다 |
| 형식 | 폼 3개 × 글 12개(공통 2 + 고유 10, 구간마다 2개) + 응답 확인 문항("2를 선택해 주세요"). 글마다 "이 글을 이해하기 얼마나 어려웠나요?" 1(매우 쉬웠다)~5(매우 어려웠다). 폼 안 순서는 섞음. 응답자 약 60명 |
| 주 분석 | 글별 체감 평균과 `difficulty_score_v2`의 Spearman ρ, 95% 신뢰구간. 응답 확인 문항을 틀린 응답자는 뺀다 |
| 성공 기준 | ρ ≥ 0.5, 신뢰구간이 0을 포함하지 않음, 글자 수의 ρ보다 높음. 0.3~0.5 부분 성공, 0.3 미만 실패 |
| 함께 볼 것 | Jo 점수, 자르기 전 GL(`metrics.gl_score`), 명사 나열 길이, 어려운 단어 개수, 글자 수의 ρ. 공통 글로 폼 간 차이. 72.7점 기준이 체감 상위 글을 얼마나 맞히는지 |
| 엔진 고정 | 10/4 버전으로 고르고, 응답이 들어온 뒤에는 엔진을 고치지 않는다. 결과를 보고 고치면 그 결과는 다시 탐색 자료가 된다. 10/9·10/13 변경은 블록 점수(`difficulty_score`, `difficulty_score_v2`)를 바꾸지 않았다(1,460개 블록 결과로 확인) |

**10/4에 바꾼 것.** 문장 수 2~3개 → 1~3개(10개 사이트로 시험하니 2~3개 조건에서는 GL 12 이상 후보가 0개. 어려운 글은 긴 한 문장인 경우가 많다). 응답 확인용 쉬운 글 → 답을 지시하는 문항. 뽑는 규칙을 스크립트로 고정. 100점(GL 12 이상) 동점 때문에 분석값을 바꾸지는 않았다. 30개를 6개씩 뽑는다고 가정한 시뮬레이션(5,000회)에서 동점의 손해는 순위 상관 0.01 정도였고(0.66 → 0.66), 동점을 피하려고 어려운 글을 빼면 범위가 좁아져 0.51로 떨어졌다.

**글 선정 도구: `select_survey_texts.py` (AI 모듈 루트).**

```powershell
.\.venv\Scripts\python select_survey_texts.py survey_urls.txt     # URL 목록(한 줄에 하나, # 주석)
.\.venv\Scripts\python select_survey_texts.py --skip-run          # 이미 돌린 결과로 다시 고르기
```

- URL마다 `run.js`(DOM 저장) → `text_extractor.py` → `difficulty_engine.py`를 돌려 `output/survey2/sites/<번호_도메인>/`에 둔다(CV·LLM·백엔드 없음).
- 조건에 맞는 긴 글을 모으고(팝업·제외 영역 글, 중복, 제목까지 품은 바깥 블록은 뺌) `candidates.csv`, 구간별로 골라 폼에 나눈 `selected.csv`(폼, 순서, 역할, 엔진 지표, 사이트, 선택자, 글), 선정 기록 `selection_log.json`, 구글폼 생성 스크립트 `create_survey_forms_v2.gs`를 만든다.
- `create_survey_forms_v2.gs`를 script.google.com에 붙여 넣고 `createForms`를 실행하면 폼 3개가 생긴다. 문항 제목 "글 N"의 N은 폼 안 순서라 응답은 `selected.csv`의 form·position으로 엔진 점수와 맞춘다. 응답자에게 내부 식별자와 점수는 보이지 않는다.
- 같은 입력과 `--seed`(기본 20261004)면 같은 결과. 어떤 구간이든 후보가 6개 미만이면 경고와 종료 코드 3. 쉬운 글(GL 5 미만)이 가장 모자라기 쉬우니 생활 안내·쉬운 말 안내문 같은 페이지를 섞는다.
- 10개 사이트 메인 페이지만으로 시험하면 후보가 22개(GL 5 미만 4, 5~7 2, 7~9 1, 9~12 6, 12 이상 9)라 본문 페이지가 필요하다.
- 테스트: AI 모듈 루트 `tests/test_select_survey_texts.py`(6개).

**분석 도구: `analyze_survey2.py` (AI 모듈 루트, 2026-10-09).** 분석 방법과 판정 기준을 응답을 받기 전에 코드로 고정했다.

```powershell
.\.venv\Scripts\python analyze_survey2.py --responses "[Uniaccess 2차 설문 1_3] ... (응답).csv" "...2_3...csv" "...3_3...csv"
.\.venv\Scripts\python analyze_survey2.py --responses 1=a.csv 2=b.csv 3=c.csv     # 파일 이름을 바꾼 경우
```

- 응답 확인 문항에서 2를 고르지 않은 응답자를 빼고, 공통 글은 세 폼을 합친다(글 32개, 응답 5개 미만인 글은 제외).
- 주 분석: `difficulty_score_v2`와 글별 체감 평균의 Spearman ρ. 95% 신뢰구간은 Fisher z(Spearman 분산 1.06/(n−3)), 부트스트랩 1만 번으로 재확인, 순열 검정 1만 번. 판정은 위 성공 기준 그대로.
- 판정에 안 쓰는 것: Jo 점수·자르기 전 GL·명사 나열·어려운 단어 개수·글자 수의 ρ, 72.7 기준의 정밀도·재현율(체감 상위 = 글 평균 > 중앙값이 주, > 3점이 보조), 반분 신뢰도(Spearman-Brown, 200번. 엔진 상관의 대략적 상한은 √신뢰도), 폼 간 수준 차이, 응답자 평균을 뺀 ρ.
- 출력: `output/survey2/analysis/report.md`, `per_text.csv`, `summary.json`. 글마다 응답 수 중앙값이 15 미만이면 "중간 결과"라고 적는다. 파일 이름의 "설문 N_3"·문항 번호가 `selected.csv`와 다르면 종료 코드 2.
- 표준 라이브러리만, seed 20261014. 테스트 14개(`tests/test_analyze_survey2.py`).
- 72.7 기준은 이 결과로 "판단"만 한다. 새 기준이 필요하면 다음 탐색 자료로 정하고 같은 설문으로 다시 검증하지 않는다.
